# Before the first public release

The app ships to testers today: a self-signed package their PC trusts by hand, and updates from a public
releases repository. This list is what's left before anyone can install it from a public link. Items marked
**decide** are the owner's call; the rest is ready or needs one command.

## Must do

1. ~~**Rewrite the repository's history.**~~ Done on 2026-10-02: the owner's chief name was in about 45 early
   commits (names in code and identifiers, and a file name), replaced with `git filter-repo` across all history
   (today's files were already clean and stayed byte-for-byte the same). A stray worktree pointer was removed too.
   `npm run privacy:history` is clean. Both repositories are public. Never push from a copy made before the rewrite
   (a backup is kept outside the repository): it would bring the old history back.
2. **A release signing key kept offline.** `apps/desktop/src/release-key.ts` pins the closed-phase key. Make a new
   one (`node packaging/release/release-tool.mjs keygen <file outside the repo>`), add it to `RELEASE_KEYS`, ship
   one release signed with the old key, then sign with the new one (`releaseKeyId` in `release.local.json`) and give
   the old key an `expires` date.
3. **Code signing for the package** (**decide**). Self-signed packages need a certificate installed by hand and
   show warnings. The options:

   | Option | Cost | Fits this project because | Watch out for |
   | --- | --- | --- | --- |
   | **Azure Artifact Signing** (was Trusted Signing) | about $10 a month | signs MSIX with a publicly trusted identity from this PC (signtool plug-in), so the local release script keeps working | individuals must be in the US or Canada; organizations in more countries; identity validation takes days |
   | **SignPath Foundation** | free for open source | EV-grade signing for OSI-licensed projects | signs only what GitHub Actions built: the package build (with its 3 GB payload) would have to move to CI first; a published signing policy |
   | **Microsoft Store** | free individual account | the Store signs the package and handles installs and updates | Store review for each release; the private-repository updater would be replaced by Store updates for Store installs |
   | **An OV certificate from a CA** | about $200–400 a year, on a hardware token | works anywhere | SmartScreen reputation builds slowly |

   Recommendation: Azure Artifact Signing if the owner qualifies (the least change to how releases are made);
   otherwise the Microsoft Store.
4. ~~**A public releases feed.**~~ Done: the releases repository is public and 0.1.21 reads it without a key.
   Testers' old keys can be deleted once everyone is on 0.1.21 or later.

## Ready, nothing to do

- **Third-party notices** are generated by every release (`scripts/licenses.mjs --notices`) and shipped in the
  package; Settings → About → Third-party licences opens them. They list where to get the source of the GPL
  programs (ffmpeg, Git), which run as separate programs.
- **A licence gate:** the release fails on a package whose licence isn't on the allow-list (CI checks the npm side).
- **A bill of materials** (CycloneDX) is published with each release. Its SHA-256 is in the signed `release.json`.
  When releases are built in CI, attest it with `actions/attest-sbom` as well.
- **OpenSSF Scorecard** runs weekly once the repository is public (`.github/workflows/scorecard.yml`).
- **Payload provenance:** every release checks that the payload is the one `hermes/pin.json` and the patch queue
  describe, and records its tree digest in `release.json`.
