## Commands

```text
npm test             # unit/regression; live bridge checks stay skipped
npm run test:bridge  # three live checks; see README "Check" for the enable flag
```

Live checks need `CHIEF_BRIDGE_SMOKE=1` and `CHIEF_BRIDGE_TOKEN` (same secret as `CHIEF_DASHBOARD_TOKEN`, process environment only). Optional `CHIEF_BRIDGE_URL` overrides `http://127.0.0.1:7790`.

## Stopping a gateway when more than one Hermes install is on the PC

`hermes -p <profile> gateway stop` on Windows is not scoped to `HERMES_HOME`. It ends the per-user scheduled task named after the profile (`Hermes_Gateway_<profile>`), and it sweeps gateway processes. On 2026-09-30 a test run of it, against a throwaway home, stopped the live install's gateway on the same PC; its guard restarted it within about a minute.

This app never calls it. To stop its own gateway, it writes Hermes's own planned-stop marker in its own profile home for its own gateway pid; the gateway drains and exits. Only then, if needed, does it end its own process tree. The code is `requestScopedStop` in `apps/desktop/src/gateway.ts`, and `gateway_smoke` in `packaging/upstream/compat.py`.

Quit asks "Chief is busy: Wait / Quit now" (a native dialog) while a turn is still ending, and the chief's words show before its turn ends. The Electron smoke test (`scripts/smoke-electron.mjs`) answers that dialog "Wait for Chief" before quitting; without it, the quit timed out whenever the timing landed in that moment. On a timeout it ends the whole process tree, or the throwaway gateway keeps running and its folder stays locked.

The gateway's `gateway.pid` appears a few seconds after `/health` answers, so a stop right after start must wait for it. A test that stops its own gateway should check that a live install on the same PC is unaffected: its `gateway-starts.log` line count doesn't change.


## Creating and removing worker profiles

Two Hermes profile helpers reach outside the profile they are given:

- `hermes_cli.profiles.create_profile` writes a command wrapper (`<name>.cmd`) into a user-wide folder on `PATH`, unless it is called with `no_alias=True`. A second install's wrapper would shadow the first's. `fleet.mint` always passes `no_alias=True`.
- `hermes_cli.profiles.delete_profile` disables the per-user scheduled task `Hermes_Gateway_<name>` and deletes the wrapper, both by name, so it can break a profile of the same name in another install. `fleet.retire` never calls it: it exports the profile (Hermes's own `export_profile`, which leaves out keys), refuses while the bot is working, and then removes only that profile's folder itself.

`hermes/tests/contract/run_fleet_contract.py` checks that minting writes no wrapper and that the archive holds no `.env` or `auth.json`.

## What the chat shows besides transcript rows

`hermes/plugins/chief-dashboard-bridge/chat_state.py`; test map: `hermes/tests/test_chat_state.py`, and the questions and live-steps checks in `hermes/tests/contract/run_chat_controls_contract.py`.

- **The chief's questions (`clarify`).** The adapter overrides Hermes's `send_clarify`, so no text prompt goes to the outbox. The bridge reads the open question from `tools.clarify_gateway` (`get_pending_for_session(..., include_choice_prompts=True)`) and answers through `resolve_gateway_clarify`. The adapter marks every question as accepting free text (`mark_awaiting_text`), so a typed message answers it too. If Hermes renames these, the contract fails at "the question comes with the transcript".
- **Notices.** Every adapter send is written to the outbox, replies included. A notice is an outbox row whose text isn't a transcript reply, or a piece of one. Hermes saves a reply's row before it sends it; if that order ever flips, a reply could flash as a notice. "⏳ Working" busy lines are never notices and never push to the phone.
- **Live steps.** A turn's rows reach `state.db` only when the turn ends. The adapter declares `supports_status_text`, so Hermes calls `set_status_text` as each tool starts. To label steps in the app's words, the plugin wraps `agent.display.build_status_phrase` (`chat_state.install_status_capture`). The wrapper notes the tool and arguments on the same thread, just before `set_status_text`. Without the wrapper, the bridge falls back to Hermes's own phrase, tidied. Deferred tools (Hermes's `tool_search` defer list) that the model calls directly are refused before they start, so they show no step. The test model uses `skills_list` for that reason.

## The bundled Second Brain toolkit

`hermes/vendor/obsidian-second-brain/` is a pinned release of the public `obsidian-second-brain` toolkit (MIT), built with its own Hermes build. It is re-vendored with `packaging/upstream/osb_vendor.py --tag <tag>`. Test map: `hermes/tests/test_provision_toolkit.py` and `hermes/tests/contract/run_second_brain_contract.py`.

- **Script calls.** The toolkit's skills run its helper scripts with `uv run --directory "$HOME/.hermes/skills/obsidian-second-brain" …`. That would make `uv` download the toolkit's dependency set, and it names the wrong folder. `provision.install_toolkit` rewrites each call to `PYTHONPATH="<site-packages>" "<the app's Python>" "<install root>/scripts/<script>.py"`. A new upstream form of the call that the rewrite doesn't match leaves a `uv run` behind; the test "never call uv" fails.
- **Left out.** The research skills (paid keys, Whisper and PyTorch downloads), `create-command` and `obsidian-retrieval-eval` (Ollama). `vendor.json` lists them.
- **Folders.** The toolkit finds folders through a `## Folder Map` table in the vault's rules file. It looks for `_CLAUDE.md`, which in this app is a pointer to `AGENTS.md`. The app's template writes the map, and `second_brain.upgrade()` appends it to an app-made `AGENTS.md` that lacks one.
- **Routines** are cron jobs in the chief's profile named `Second Brain: …`; the app finds them by name. Renaming one in Hermes makes the app create it again.
- **Second Brain first.** `skills.auto_load: [second-brain]` pins the skill into every new session. `CRITICAL_FACTS.md` is never copied into it: the bridge registers a system prompt section (`chief-critical-facts`, `second_brain.facts_prompt`) that reads the file when each of the chief's conversations starts, in every chief process (gateway, jobs, terminal). Bots get the skill through `share_with()` and read the file when they need it; the toolkit comes through `skills.external_dirs`. Copying the facts into the skill made it churn in Fleet Health and undid hand edits within a minute.
- **Skills the app writes must say so, and must not name a moving path.** Each is recorded with its content hash (`.chief-bundled.json` for bundled skills and the toolkit, `skills/.chief-generated.json` for the rendered Second Brain skills), and the learning ledger labels a file matching its record `installed`, not an edit. An edited one is kept and no longer updated. A path in a skill's text must not change between versions: the installed app's folder is named for its version, so the toolkit calls plain `python` (the agent's own, see below). Otherwise every update rewrites those files and Fleet Health reports churn.
- **The default SOUL.** `seed_soul()` replaces an unedited earlier default. It recognizes those by digest (`_PREVIOUS_DEFAULT_SOULS`). When `second_brain/SOUL.md` changes, a unit test fails until the old digest is recorded.

## Threads, routines and usage

`threads.py`, `routines.py` and `usage.py` in `hermes/plugins/chief-dashboard-bridge/`. Test map: `hermes/tests/test_threads.py`, `hermes/tests/test_usage.py`, `hermes/tests/contract/run_usage_contract.py`, `hermes/tests/contract/run_routines_contract.py`, and the thread and routine checks in `hermes/tests/contract/run_chat_controls_contract.py`.

- **A thread is a chat id.** The main thread is the home channel (`owner`). Others are `owner.t-<8 hex>`, so their session keys are `agent:main:command_center:dm:owner.t-…`. `data.resolve_session_key` skips those keys when it looks for the main chat. If Hermes changes how it builds session keys from chat ids, the contract fails at "their transcripts stay apart".
- **Fresh start answers Hermes's confirmation.** `/new` asks through `tools.slash_confirm`. The bridge waits up to 8 s for `get_pending(session_key)` and then sends `/approve`. If Hermes stops asking, the fresh start still works; if it renames the module, the bridge never approves and the contract fails at "a fresh start is accepted".
- **A bot's routine can't deliver into the app itself.** Hermes's pre-run check blocks a job whose delivery platform the job's profile doesn't serve (`cron/scheduler_preflight.py`), and bots don't serve the Command Center. A bot's routine is saved with `deliver: local`. Its thread is kept in the chief's profile (`routine_threads.json`), and `routines.relay()` (watch loop, about every 10 s) posts each new run's `## Response` from the job's output folder into that thread. The last run relayed is in `routine_relayed.json`. If Hermes changes its output file layout, nothing is relayed, and the contract fails at "a bot's routine runs and reports into the main thread". The chief's own routines still deliver through Hermes (`command_center:<chat>`).
- **Built-in routines are found by name** (`Second Brain: …`, `Fleet: …`), as before.
- **Usage is read from Hermes's per-model ledger, not the session row.** The model picker switches a live conversation without a new session, and `sessions.model` keeps the model the session *started* on (`COALESCE(model, ?)`). So `usage.py` reads `session_model_usage`: one row per session, model, provider and task, added to on every API call with the model that call used (task `''` is the conversation, other tasks are titles, compression and so on). Whatever a session's totals hold beyond its ledger rows stays with the session's own model. The run contract fails at "the ledger splits the conversation by model and provider" if Hermes stops recording it that way.
  - **Days come from the bridge's own journal** (`usage_journal.db` in the chief's profile), because Hermes keeps only running totals: a long conversation's row covers its whole life, and dating it by its last call put weeks of use on one day (0.1.12–0.1.15 showed about 50× the real tokens for "today"). Each sync (on every read, and every 5 minutes through the watch loop's budget check) records only what each row grew since its mark, on the day of the row's latest call. A row seen for the first time is spread over its active days by the chief's replies (assistant messages) per day. `exactSince` in the summary is when the journal began; earlier days are estimates, and the Usage page says so.
  - The journal keeps usage after Hermes prunes sessions, and a shrinking total never makes a negative day. Deleting the journal rebuilds it on the next read, with every day before then estimated again.
  - Provider dashboards count days in UTC; the journal uses this PC's local days, so a single day can differ a little near midnight.
  - A row's cost is its actual cost when Hermes has one, else its estimate. Tokens with no cost count as unpriced, not free. The budget lives in the chief's profile (`usage_budget.json`). One notification is sent per month, and nothing is ever stopped.

## Second Brain formats

`second_brain.py`, `second_brain/template-wiki/`, the `skill-*` folders beside it, `drop_gate.py`, and `apps/web/lib/server/today-index.ts`. Test map: `hermes/tests/contract/run_second_brain_contract.py` (the wiki section), `apps/web/tests/today-kanban.test.ts`, `apps/web/tests/second-brain-setup.test.tsx`.

- **The rules file decides.** `manual()` treats `_CLAUDE.md` as the folder's own manual unless it is the app's short pointer (`# Rules for agents` … `[[AGENTS]]`), then `AGENTS.md` unless it is the pointer the other way. If those pointer texts change, an app-made vault looks like an owner's own manual, and keep-mode setup adds nothing to it.
- **Format detection:** `wiki/` plus `raw/`, or a `_CLAUDE.md` mentioning both, means the wiki format. A PARA vault with a `wiki/` and a `raw/` folder of its own would be detected as wiki; setup then offers a one-click switch back.
- **Folder Map.** The toolkit's skills read the `## Folder Map` table in `_CLAUDE.md` (`references/folder-map.md`); the wiki template's manual has one. Without it, the toolkit falls back to its wiki-style defaults, which match.
- **The drop gate** is a cron `script` in the profile's `scripts/` (Hermes runs scripts only from there). It runs from the vault (the job's `workdir`) and prints `{"wakeAgent": false}` when there is nothing to file. If Hermes changes the wake-gate contract (`cron/scheduler_prompt.py`), the contract fails at "an empty drop folder never wakes the model".
- **The morning brief is mirrored into the chat session** (`attach_to_session`). Hermes stores the copy as a user row starting `[Cron delivery:`; `data.transcript` hides those rows, and the notice shows the brief once. If Hermes changes that prefix, the brief appears twice, once as if the owner had sent it. `test_bridge` covers the filter.
- **Kanban boards** are recognized by `kanban-plugin:` in the properties block only. The column mapping is by keywords (Backlog, This Week, In Progress, Waiting On, Next Week, Done; unknown headings count as Backlog), and reading stops at `%%`.

## Adopted installs

`apps/desktop/src/store.ts` (`adopted`), `apps/desktop/python/provision.py --adopted`, `second_brain.adopted()` and `learning.ensure()` (both read `CHIEF_ADOPTED`), and `packaging/migrate/adopt.py`. Test map: the adopted section of `run_second_brain_contract.py`, `AdoptedInstallTests` in `test_provision_toolkit.py`.

- **The owner's skills win by name.** The app looks for a same-named skill anywhere in the profile's skills and its `skills.external_dirs`. A skill counts as the app's only if its frontmatter says `author: Chief Command Center`; anything else is the owner's and is never shadowed. Renaming that author line in a bundled skill makes the app treat its own skill as the owner's.
- **The toolkit is the owner's** when an external skills dir holds `obsidian-second-brain`. The always-loaded skill's `{{toolkit}}` then points there. If the owner deletes it later, the app reinstalls its own only when not adopted.
- **The old `command-center` plugin must stay off:** the app's bridge registers the same platform. `adopt.py` moves it aside and removes it from `plugins.enabled`.
- **The old launchers** (the guard task and Startup VBS that start this profile's gateway) are found by their reference to `profiles\<profile>\gateway-service`. `adopt.py --rollback` turns them back on.
- **Fleet Health runs the app's ledger** on the install's own report folder (`learningDir`) unless `ownLedger` is set. `learning.adopt_ledger()` points any job whose script is named like `learning_ledger` at the copy in `scripts/learning_ledger.py` and records the old script in `<learning>/ledger-switch.json`; `ownLedger: true` (CHIEF_OWN_LEDGER) restores it at the next start. The contract checks both directions.
- **`gateway.standalone: true`** on the chief profile (set by provisioning) is what lets the app run that profile's gateway at all. Without it, Hermes 2026.9.x refuses a named profile's own gateway unless a Hermes launcher for that profile is registered on the Windows account. Hermes calls the key a temporary shim, "removed once multiplexing gaps are fixed". When an upstream pin drops it, the compatibility suite's "gateway start, bridge, stop" fails (exit 78), and the app must move to running the host gateway from the default profile.

## The chief's name

`apps/web/lib/identity.ts`, `isChief` in the bridge's roster (`data.py`) and `apps/web/lib/types.ts`. Test map: `apps/web/tests/last-chief.test.ts`, and the sample chief "Nova" throughout the tests.

## Phone access (Tailscale Serve)

`apps/desktop/src/tailscale.ts`, the `phone:*` IPC in `apps/desktop/src/main.ts`, `apps/web/components/phone/`, `apps/web/lib/tailnet-guard.ts`, `apps/web/proxy.ts`. Test map: `apps/desktop/tests/tailscale.test.ts`, `apps/web/tests/phone-settings.test.tsx`, `apps/web/tests/phone-this-device.test.tsx`, `apps/web/tests/tailnet-guard.test.ts`.

- **The app owns exactly one Serve entry.** It reads `tailscale serve status --json`, marks the HTTPS entry whose `/` handler proxies to `127.0.0.1:<ui port>` as its own, and changes only that one (`serve --bg --yes --https=<port> http://127.0.0.1:<ui>`, and the same with `off`). It never runs `serve reset`: the owner may serve other things (another port on the same PC). Serve's HTTPS ports are 443, 8443 and 10000; when 443 is taken it uses the next free one.
- **Serve waits on a consent link** when the tailnet hasn't allowed Serve or HTTPS yet. `enableServe` returns the first `https://login.tailscale.com/…` link it prints and ends the wait (20 s at most). If Tailscale changes that output, Turn on reports "didn't answer in time" instead of offering the link.
- **The CLI's JSON shapes** (`status --json`: `BackendState`, `Self.DNSName`, `Self.UserID` → `User[id].LoginName`, `CertDomains`; `serve status --json`: `Web["host:port"].Handlers["/"].Proxy`) are parsed in `parseStatus` / `parseServe`. A change there shows as "isn't answering" or a step stuck at to-do.
- **"Only you" is `CHIEF_DASHBOARD_TAILSCALE_USER`** in the desktop store's `webEnv`, which the dashboard server reads at start: changing it restarts that server (about a second). An empty value lets every login on the tailnet in (the behaviour before this page), so turning phone access on the first time sets it to the PC owner's login.
- **The dashboard port can move** (3000 busy at start, `choosePorts`). `phoneServe` in the store remembers the Serve port and the ui port it pointed at, so the page can say the address points nowhere and offer Fix it.
- **On the phone, Settings → Phone** is the page opened through Serve (a non-loopback host). Android's install button needs `beforeinstallprompt`, captured by `lib/install-prompt.ts`, which `command-shell.tsx` imports so it listens from the first moment. iPhone allows Web Push only from the Home Screen app, so alerts stay disabled in Safari with a reason.
- **The bridge's push routes** `push/subscriptions` (a count only), `push/test` and `push/unsubscribe` are on the proxy allow-list for this page.

## Update history

`apps/desktop/src/release-history.ts`, `onVerified` in `apps/desktop/src/updater.ts`, `apps/web/lib/server/update-history.ts`, `apps/web/components/updates/update-history.tsx`. Test map: `apps/desktop/tests/release-history.test.ts`, `apps/web/tests/update-history.test.tsx`.

- **Every release description is kept as signed**, in `<appDir>/release-history/<version>.json` + `.sig`, verified before writing and again when the desktop reads it. The dashboard server reads the same files (it trusts the app's own folder and doesn't re-verify), so the phone sees the list too.
- **GitHub feeds sync the whole list** with `GET /releases?per_page=100`, then the two small assets of each release not kept yet. A folder feed keeps only what its checks have seen. Over 100 releases, the oldest stop arriving (add paging then).
- **Install dates** come from `update-history.json`, written on the first start of each version (`recordInstall` in `boot()`), from 0.1.13 on. Earlier installs show only their release dates.
- **One card at a time:** while a newer version is offered (even after Later), What's new stays hidden, and notes for a version a newer update replaces are marked seen instead of waiting (`newer` from `useUpdates()` in `command-shell.tsx`).
- **What's new** shows the running version's notes once per device (`chief-whats-new-seen` in localStorage), for 14 days after an update that replaced an older version, and only when its notes are kept.

## Installing an update

`prepare()` and `restart()` in `apps/desktop/src/updater.ts`; `apps/desktop/src/update-helper.ts` (the helper's copy, job, stage, hand-off, result) and `install-package.ts` (WMI launch, the fallback installer); `readChiefLook`, the updater's deps and `markReady` in `main.ts`; `bringToFront` and `announceUpdate` in `window.ts`; the helper itself in `apps/desktop/updater-helper/` (built by `apps/desktop/scripts/build-updater.mjs`). Test map: `apps/desktop/tests/updater.test.ts`, `update-helper.test.ts`, `install-package.test.ts`; `apps/web/tests/update-card.test.tsx`, `chief-look.test.tsx`.

- **Prepare, then restart.** A release is downloaded, backed up for (when it brings a different Hermes) and staged by Windows while Chief runs (`ChiefUpdater.exe stage`, a hidden child); the restart only registers the staged package. A staging failure isn't an error: the restart then installs the whole package, with progress in the same window. Windows' own maintenance clears a staged package nobody registers; nothing in the app removes one.
- **One prepare and one restart at a time.** Both keep their running promise and hand it to any second call, so a double click, the card's "restart when Chief's done" retry, the same card in Settings or the automatic prepare after a check can't stage or hand Windows the package twice (0.1.13 was installed twice, 34 s apart, before this). A check never knocks a release that is downloading, preparing, ready or restarting back to "available".
- **The helper runs from a copy outside the package** (`<appDir>\updater\ChiefUpdater-<version>.exe`): the copy inside is replaced by the very install it performs. `apply` is started through WMI (`Win32_Process.Create` with `ShowWindow`), so it has no package identity and isn't in the app's job: Windows shuts every process of the package down to replace it.
- **Two installers never run at once.** The app quits only after the helper writes `shown-<version>`; a helper that doesn't show its window within 10 s is killed (by the pid WMI reported) before the fallback runs. The fallback is the old `Add-AppxPackage` script, run as `conhost.exe --headless` with `ShowWindow = 0`: on Windows 11 a console started any other way opens in Windows Terminal, which `-WindowStyle Hidden` can't hide (that window was the "looks crashed" report).
- **Smart App Control can block the helper.** Testers trust our certificate only in `TrustedPeople`, which covers the MSIX, not a standalone exe, so on a PC with Smart App Control on, the copied helper may not start. The fallback covers it; the update then takes about a minute with no window but the card's "reopens by itself" line.
- **Register only once the package is quiet.** The helper waits for the app's pid to exit and then for no process to run from the old install folder (20 s, then forces). Registering while the old desktop container is still alive is a known MSIX failure (`0x80070020`, unlaunchable until sign-out); if activation fails that way, the helper says Windows needs a restart instead of looping.
- **The update window closes when the reopened app is up**: the app writes `ready-<its version>` in `<appDir>\updater` on its first page load (the boot page). A failed install reopens the old version, so the helper waits for `ready-<from>` then. Stale markers are removed before each hand-off.
- **Failures reach the next start.** The helper (and the fallback script) write `update-result.json`; the next start reads it once, logs it and shows "The update to X didn't finish: … You're still on Y" with Try again.
- **The window shows Chief's own face and colour**: `window.__chiefLook()` (`components/chief-look.tsx`) rasterizes a still, idle copy of the face kept off-screen (computed paint inlined, `lib/face-snapshot.ts`), read by `readChiefLook` at the start of `stopChief`, before the page dims. No face (a photo that won't load, an older page) falls back to the app icon.
- **The reopened window must be raised.** The helper activates the app through `IApplicationActivationManager` after `AllowSetForegroundWindow`, which normally brings it to the front; the fallback relaunches it as a hidden background process, and Windows' focus-stealing protection keeps that window behind the others. The first start after an update (`lastVersion` older than this version) still raises it with a brief always-on-top, flashes the taskbar button if focus is withheld, and shows a "Chief updated to …" notification once Chief is up.
- **`logs\update-install.log`** has the staging and helper lines (`staging …`, `apply 0.1.30 -> 0.1.31: <step>`), or the fallback installer's, then the app's own: `result …`, `reopened <version>`, and `ready <version>; window shown/hidden`. A graphics-process crash (a blank window) goes to `logs\desktop.log`.
- **An installed app updates with the code it already has.** The release that brings a change to this flow still installs the old way; the new flow shows from the update after it.
- **A saved update key can block a public repository.** GitHub answers 401 to an expired or revoked token even where
  no token is needed, and testers kept the keys they were given while the releases repository was private (before
  0.1.21). From 0.1.32 a refused key is retried without it (`githubApi.call`); when that works the key is dropped for
  the session, `keyRefused()` is true, and Settings says so beside **Remove key**. A private repository still reports
  the refusal. Apps before 0.1.32 can't do this: a tester stuck there pastes a fresh key or installs from the kit.
- **Without a key, files come by their download links, not the API.** GitHub allows 60 API calls an hour per network
  without a key; `/releases/assets/<id>` counts, `browser_download_url` doesn't. Before 0.1.32 the history sync fetched
  two assets per release it hadn't kept, so an app far behind spent its hour in one check. With a key the API path
  stays (a private repository's assets need it). A check is now one API call.
- **A version chosen from the history** (`installVersion`) is kept against the daily check (`chosen`): the check would
  otherwise offer the latest instead. It downloads by tag (`source.select`), so it needs a GitHub source; its
  description comes from the kept, verified history. `older` marks a state whose version is older than the running one.
- **A face's body never moves with the eyes' jumps.** Busy eyes snap between holds (`scanGaze`, 60 ms); the head,
  lean and roll follow `headGaze` (the eyes' last 0.6 s through a raised-cosine window). Driving the body from
  `scanGaze` made a Bubble twitch. A mood change blends over `MOOD_BLEND_S` (`blendFor` in `useRig`, noticed by
  whichever draws first), and the rig's redraw on a mood change uses `clockTime()`, never `t = 0`: drawing at 0 showed
  the pose from the clock's start for one frame. `tests/face-motion.test.ts` measures per-frame steps.
- **Chief's ring is the voice's.** Thinking and working breathe the glow (`pr-breathe`); the ring and the orbiting
  dots stay off then (the orbit is only for the celebration moment). `tests/face-motion.test.ts` reads the CSS.
- **Early updates are GitHub prereleases.** Without Early updates the source reads `/releases/latest`, which GitHub never points at a prerelease; with it, `/releases?per_page=20` and the highest version carrying a `release.json`, drafts never (`newestRelease`). `release.mjs --channel early` publishes as a prerelease and skips the tester kit and `afterRelease`; `--promote` flips the same release to latest and runs them. A version is never rebuilt between the two.

## The message box hint

`apps/web/components/chat/composer.tsx`, `.composer-hint` in `apps/web/app/globals.css`. Test map: `apps/web/tests/composer-hint.test.tsx`.

- **The hint is an overlay, not the textarea's placeholder.** A native placeholder that wraps (long hints like "Add to what <name> is doing…" beside the Stop and Send-after buttons) made the box two lines tall, misaligned it with its buttons, and could be cut off mid-line when the buttons slid in after the height was measured. ## Releases and testers

`scripts/release.mjs`, `scripts/tester-kit.mjs`, `packaging/tester/`, `apps/desktop/electron-builder.config.cjs` and `builtInFeed()` in `apps/desktop/src/release-source.ts`. Test map: the "update source a build carries" tests in `apps/desktop/tests/release-source.test.ts`; `install-chief.ps1 -CheckOnly` on an unzipped kit.

- **A release build carries its update source.** `release.mjs` sets `CHIEF_UPDATE_FEED=github:<releasesRepo>`, and electron-builder writes it into the packaged `package.json` as `chiefUpdateFeed` (`extraMetadata`). ## Desktop and dashboard hardening

`apps/desktop/src/guards.ts`, `boot-protocol.ts`, `session.ts`, `electron-builder.config.cjs` (`electronFuses`), `apps/web/proxy.ts`, `apps/web/lib/loopback-session.ts`, `securityHeaders` in `apps/web/next.config.ts`. Test map: `apps/desktop/tests/guards.test.ts`, `apps/web/tests/loopback-session.test.ts`, `apps/web/tests/tailnet-guard.test.ts`, `apps/web/tests/backup-routes.test.ts` (phone limits).

- **Origins are parsed, never prefix-matched.** A window the dashboard opens inherits the preload (the whole `chiefDesktop` API), so `windowOpenDecision`, `navigateDecision` and the permission handlers compare `new URL(url).origin` exactly. Every IPC channel goes through `handle()` in `main.ts`, which checks the sender frame.
- **The boot page has its own scheme** (`chief-boot://app/boot.html`). With the `grantFileProtocolExtraPrivileges` fuse off, a `file://` page can't read inside `app.asar` (found by booting an unpacked fused build: ERR_FILE_NOT_FOUND and a hung window). The main process serves it. Fuses only exist in a packaged build: check a change to them with `electron-builder --win dir` and `npx @electron/fuses read --app <exe>`, then boot that build on a throwaway data folder.
- **The loopback session.** With `CHIEF_SESSION_SECRET` set (the desktop app sets it each launch), the proxy (`proxy.ts`) admits a direct-loopback request only with the `chief_session_<port>` cookie the app sets on its window; `/api/healthz` is the only exception (the readiness probe). Anything the desktop app itself fetches from the dashboard must send the cookie (`finishInDashboard` does). A browser on the PC gets in through the tray's Open in browser (a 60-second HMAC ticket). Without the variable (dev servers) nothing changes. `NextRequest.nextUrl` says `localhost` for `127.0.0.1`, so the ticket redirect is built from the Host header, or the cookie lands in the wrong jar.
- **Running the unpackaged app beside the installed one** needs its own `--user-data-dir`: both are `@chief/desktop`, so they share Electron's single-instance lock, and the second launch only asks the installed app to show its window.
- **The CSP** allows inline scripts (Next's bootstrap) but limits connections, pictures, media, fonts and frames to the dashboard itself. A feature that loads anything from another host (a CDN, an external image) needs a deliberate change in `securityHeaders`. Next's config loader doesn't resolve local imports, which is why the headers live in `next.config.ts`.

## Live updates

`hermes/plugins/chief-dashboard-bridge/changes.py`, `outbox.py`, `_sse` and the long-poll in `server.py`; `apps/web/lib/live.ts`, `apps/web/lib/poll.ts`, the `events` branch of `apps/web/app/api/bridge/[...path]/route.ts`. Test map: `hermes/tests/test_changes.py`, `apps/web/tests/live.test.ts`, `run_chat_controls_contract.py` (everything that rides on the long-poll), the capture tool's `chk-idle-requests`.

- **One change signal.** Long-polls and `/events` wake on `changes.bump()`. Its sources are the outbox, questions (asked or retired), live steps and broadcasts. A watcher also reads `PRAGMA data_version` on the chief's `state.db` and the install's `kanban.db`, and compares the in-memory working sessions and the main chat's pending approval, every 250 ms. A change with no signal still shows within the 2 s fallback re-check. A new kind of change the dashboard shows needs a bump, or it waits for the fallback.
- **The outbox is read incrementally** and compacted past 2 MB (30 days, never fewer than 500 rows). A scheduled job run by a separate Hermes process can append while the file is compacted, so compaction gives up if the file grew meanwhile. An `after` id that isn't there returns nothing: the desktop notifier pages with it.
- **The page's live channel** is one EventSource. Pollers pass `{ wake: liveWake }` and an interval built with `liveInterval(fast, relaxed)`. While the channel is up, the snapshot refreshes on change (every 30 s otherwise) and the ping every 15 s. When it drops, they go back to 2.5 s and the channel retries with backoff (2 s doubling to 30 s), so a down gateway isn't hammered. "Stale" thresholds in the status sheet follow the channel (`useLiveConnected`). Measured: idle bridge requests went from 30 to 6 per 30 s.

## Window, palette and shortcuts

`apps/desktop/src/main.ts` (`titleBarOverlay`, `setJumpList`, `runAction`), `apps/desktop/src/guards.ts` (`DESKTOP_ACTIONS`), `apps/web/lib/shortcuts.ts`, `apps/web/components/command-palette.tsx`, `apps/web/app/globals.css` (`.app-drag`, `.titlebar-clear`, view transitions). Test map: `apps/web/tests/command-palette.test.tsx`, `apps/desktop/tests/guards.test.ts`.

- **The window draws under Windows' caption buttons** (`titleBarStyle: "hidden"` + `titleBarOverlay`, 60 px tall). Anything at the top right must keep clear: headers use `titlebar-clear`, which reads the overlay's width from `env(titlebar-area-*)`. A full-screen layer (onboarding) needs its own `app-drag` strip, or the window can't be moved. Not yet tried in the MSIX package: Windows may not let a task start the packaged exe by path; if it doesn't, the tray menu still has the same items.

## Supervision, start-up and logs

`apps/desktop/src/supervisor.ts`, `boot.ts`, `runtime.ts` (`provisionKey`, `pycacheDir`), `logger.ts`, `diagnostics.ts`; `apps/web/lib/server/backup.ts` (the backup lock). Test map: `apps/desktop/tests/shell.test.ts` (Supervisor), `boot.test.ts`, `logger.test.ts`, `diagnostics.test.ts`; `apps/web/tests/backup-routes.test.ts`.

- **A child the supervisor ends itself** (not ready in time, or failing health checks) is recorded by pid, so its exit isn't a second crash. A new way of ending a child must go through `end()`, or its exit restarts it again.
- **Health checks** call `/health` (gateway) and `/api/healthz` (dashboard) every 30 s with a 5 s timeout; three failures in a row restart the child. A slow machine that can't answer `/health` in 5 s while busy would be restarted: raise the timeout before lowering the interval.
- **Provisioning is skipped** while `provisionKey()` is unchanged: app version, Hermes build, bridge port, adoption, Hermes root, and the plugin files' names, sizes and times. Something new that provisioning depends on must go into the key, or it won't run when that changes.
- **`PYTHONPYCACHEPREFIX`** points at `<data>\pycache` for every bundled Python. Deleting that folder is safe (the next start compiles again, about 6 s longer).
- **The log redacts** the token and session secret by value (`log.addSecret`), plus `Bearer …`, `token=`, `key=`, `open=` and similar. A new secret must be added with `addSecret` as soon as it exists.
- **The backup lock** (`<app data>\backup-running.json`) holds the engine's pid; a pid that is gone, or a record older than 6 hours, is cleared. Windows can reuse a pid, so a stale record within 6 hours can at worst make the dashboard say a backup is running until the record expires.

## Bridge routes and Hermes names

`hermes/plugins/chief-dashboard-bridge/routes.py` (the route table), `hermes_api.py` (the Hermes names the bridge uses), `apps/web/lib/proxy-policy.ts` (the proxy's allow-list). Test map: `hermes/tests/test_routes.py`, `test_hermes_api.py`; the upstream suite's "Hermes names the bridge uses".

- **A new bridge route** goes in `routes.py` with its body limit (1 MB unless it needs more) and `dashboard=True` only if the page calls it; then add it to `proxy-policy.ts`. `test_routes.py` fails until both agree. Routes the page never calls (`/outbox`, `/outbox/notify`, `/voice/model/use`) stay off the proxy.
- **A new Hermes import** in the plugin goes in `hermes_api.CAPABILITIES` under the feature that needs it, or `test_hermes_api.py` fails. Code that must not fail quietly reads the name with `hermes_api.get()` (approvals do): a missing name is logged once and shows in Status.
- **A route with an id in the middle** (`/look/{id}/pet`) is written with `{id}` in `routes.py` and as `"POST look/:id/pet"` in `proxy-policy.ts`'s `bridgeTemplates`; `test_routes.py` compares the two lists. A `raw=True` route (the photo upload, `PUT /look/{id}/avatar`) gets its body as bytes; the dashboard proxy must also export that method.
- **Bot looks write through Hermes's `_configure_ui_meta`** (`looks.py`), whose body uses `tui_gateway.server`'s globals (`json`, the ui_meta lock) and only works once that module rebinds it. The gateway doesn't load the TUI server, so `looks._configure_fn` runs the same code over its own module plus those two names (or uses the server's bound copy when it is loaded). If Hermes adds another server global to that body, every save fails as "Hermes didn't save the look"; `run_looks_contract.py` catches it. `persona.rename` still writes `profile.yaml` directly (no revision bump), so a rename racing a look save can drop one of them.
- **The legacy Discord paths** stay until an install's diagnostics show it doesn't use them: `/health` lists any used since the gateway started (`legacy`), and the bridge log has a warning the first time.

## Releases, keys and the payload record

`scripts/release.mjs`, `packaging/release/release-tool.mjs`, `packaging/payload/provenance.py`, `apps/desktop/src/release-key.ts`, `apps/desktop/src/updater.ts` (`prune`, `rollback`), `scripts/licenses.mjs`. Test map: `apps/desktop/tests/updater*.test.ts`, `hermes/tests/test_payload_provenance.py`.

- **A release is a draft until the version is pushed.** A failure before the push deletes the draft and restores the version files; after the push the draft is kept and the error says how to finish (`release-tool undraft`). `drop-draft` refuses to delete a published release.
- **The payload must have a provenance record** or the release stops. `stage.py` writes it; a payload built before it existed gets one with `python packaging/payload/provenance.py --payload <dir> --write` (check first that its source has the current patches: `git apply --check -R` each patch in the prepared source). Editing a file inside the payload after the build fails the check on purpose.
- **Release keys rotate through `RELEASE_KEYS`.** `release.mjs` reads the list from `release-key.ts` by pattern (`{ id: "…", publicKey: "…" }` on one line), so keep that shape. An installed app trusts only the keys of its own version: a new key must ship in a release signed with an old one before anything is signed with it.
- **`updates\` keeps two packages:** the newest download and the installed version's own. "Go back" needs the latter; never prune at start-up (that would delete it).
- **Licences:** a new dependency whose licence isn't on the allow-list (or that has no licence metadata) fails the release; add a reviewed entry to `REVIEWED` in `scripts/licenses.mjs` only after reading its licence.
- **The dashboard pins its own root** (`outputFileTracingRoot` and `turbopack.root` in `apps/web/next.config.ts`). The repository root has a `package-lock.json` (Python tooling), and without the pin Next takes the repository as the workspace and nests the server at `.next/standalone/apps/web/server.js`, which the desktop app and the release can't find. After changing either setting, delete `apps/web/.next` before building: a cached build keeps the old root.
- **No links in the standalone build.** Turbopack can write a symbolic link into `.next/standalone/.next/node_modules` (a hashed package alias pointing into this checkout). MakeAppx refuses links ("You can't add folders or devices to the package"), and the target wouldn't exist on another PC; `apps/web/scripts/standalone.mjs` replaces each link with a copy.
- **A z-index inside a pane must stay inside it.** Sheets over the whole app sit at `LAYER.sheet` (60) and are portaled to the body, so anything in a pane with a higher z-index (the orbit's front seats and its "+N" badge use 60 and 70) paints over an open sheet unless its container is `isolate`. Give such a container `isolate`. (The offline dimming filter hides the bug, because a filter also isolates, so test it online.)
- **The chat platform must implement Hermes's media senders** (`send_image_file`, `send_document`, `send_video`, `send_voice` in `adapter.py`). Hermes's defaults post "Couldn't deliver the … attachment", and a new media method upstream would do the same until it is added here.
- **Windows logos live in `apps/desktop/build/appx/`.** electron-builder takes the package's Start menu, taskbar and tile images from there and silently falls back to its own sample logos for any that are missing. The `.targetsize-*` files make it run makepri (the package then carries `resources.pri`). Regenerate them with `node apps/web/scripts/gen-pwa-icons.mjs`, never by hand.
- **Settings → Tools leans on Hermes's tool-picker internals** (`_visible_providers`, `_is_provider_active`, `apply_provider_selection`, the image model catalogs, `tools.web_tools._get_search_backend`), listed under "images and web search" in `hermes_api.py`. Hermes's own dashboard uses the same functions (`hermes_cli/web_routers/tools.py`), so read that file first when an upgrade breaks the page. Row names are the ids the app sends back (`"Exa · Free (keyless)"`): a renamed row only drops out of the recommended list.
- **A drag strip takes clicks from whatever is drawn over it** in the desktop app (Electron adds `app-drag` regions and subtracts `no-drag` ones in page order, regardless of z-index). Controls inside an `app-drag` header are covered by the rule in `globals.css`; controls floating over a separate strip need `app-no-drag` on their container, and content that scrolls under one needs `app-clickable`. Browsers ignore drag regions, so only the desktop app shows the bug; `tests/drag-regions.test.ts` guards it. A synthetic `WM_NCHITTEST` can't confirm a fix: it doesn't see Electron 44's drag regions.
- **Anything at the window's top-right corner sits under Windows' minimize, maximize and close** in the desktop app (Window Controls Overlay, 60px tall, `--wco` wide). Headers there use `titlebar-clear`; `Sheet` adds it for right-hand panels over the whole window. Browsers have no overlay (`--wco` is 0), so only the desktop app shows the bug. To check a fix, use a real click in an Electron window with the app's `titleBarOverlay`: synthetic hit tests don't see it.
- **Patches must keep LF line endings.** GitHub's Windows runners check out with `core.autocrlf=true`, which turned `hermes/patches/*.patch` into CRLF and made `git apply` refuse them (the Hermes compatibility workflow failed on every push until this was found). `.gitattributes` marks `*.patch -text`, and `prepare_source.py` clones upstream with `core.autocrlf=false`.
- **`stage.py` needs a Python 3.14 host.** Upstream's bytecode check names the expected `.pyc` files with the host interpreter's tag, and the payload's Python is 3.14, so an older host reports every module as uncompiled at the end of the build. `stage.py` now refuses an older Python up front, and the workflows that build the payload use 3.14.
- **An update must name the drive Chief is on.** Windows stages a package on its default app drive unless `Add-AppxPackage -Volume` says otherwise, so both `install-chief.ps1` and the updater (`install-package.ts`) find the app volume holding the current install and pass it. Checked with `-Plan` and a parser test; a real install on a second drive can't be tried on a PC whose own Chief is installed (same package identity), so try it on another PC before relying on it.
- **The first turn after a fresh gateway start can wait** on GitHub's Windows runner ("Another Hermes process is using this session") while the setup's own Hermes commands let go of the session. The chat-controls contract sends a warm-up message and waits for its answer before the timed checks; until it did, whichever check sent first failed there (the bridge-token probe for a long time, which looked like a stuck terminal). If the probe ever gets no answer on CI with the turn still running, it is reported as skipped with the step, after stopping that turn.
- **Never toggle a `filter` on the whole phone view.** The outage dim used one over a subtree holding a canvas, masks and a backdrop-filter; turning it on and off blanked frames on phone browsers. The phone dims with an opacity overlay (`command-shell.tsx`); the link counts no failures while hidden and gets `RESUME_GRACE_MS` on return.
- **The service worker caches only `/_next/static/`**, cache-first: those files are named for their content, so a kept copy is never stale. Never let it cache pages or `/api/`: an update would then show the old app. Its cache is `chief-code-v1` (bump the name to drop every kept file).
- **The bridge proxy's time limit is for the answer to start** (`app/api/bridge/[...path]/route.ts`): a limit over the whole body cut big answers to phones off half-way. A new slow route needs its own budget there (the report summary has a minute).
- **Drain every pipe a child process writes to.** `runJsonTool` (`apps/desktop/src/python.ts`) read only stdout; the backup engine reports progress on stderr four times a second, so on a large setup the pipe filled and the 0.1.25 backup before the first start blocked forever (0 % CPU, no I/O, the app stuck at "Backing up"). A child spawned with `pipe` must have both stdout and stderr read or sent to a log; `tests/python.test.ts` writes 40,000 stderr lines.
- **Never put the payload's `venv\Scripts` on a PATH.** Its `pyvenv.cfg` names the release PC's folder, and every launcher in that folder starts the venv's `python.exe`, which fails with exit 103 anywhere else (it works on the release PC, so local runs hide it). Hermes itself puts it first on every Hermes process's PATH at start (`pm/environments.py`), so the app's patch 0004 puts the interpreter's own folder first instead when the venv's `home` is gone; the bundled packages come from the PYTHONPATH Hermes sets. The app's own processes run the base Python with PYTHONPATH. A copy of the venv's launchers elsewhere (0.1.22 to 0.1.24) doesn't help: inside an installed MSIX app they can't start its Python ("Access is denied", exit 101). Test a Python change with the payload folder renamed, so the folder its venv names is really gone (`subst` leaves it in place and proves nothing), and ideally in an installed package. Running Hermes from a payload writes `hermes-agent/.hermes/bin` shims into it; provenance leaves that folder out.
- **Background work comes from Hermes's async delegation registry** (`tools.async_delegation.list_async_delegations`, listed in `hermes_api.py`), matched to the chat by `session_key`. An upgrade that renames record fields (`goal`, `goals`, `task_indexes`, `children_activity`, `dispatched_at`) silently empties the card: the chat-controls contract's "background tasks show" check catches it.
- **Background results are recognised by Hermes's wording** (`lib/background-report.ts`: `[ASYNC DELEGATION BATCH COMPLETE`, `--- ✓ TASK n/m: … (status=…) ---`, `[IMPORTANT: Background process …`). After a Hermes upgrade, regenerate `apps/web/tests/fixtures/background-reports.json` with Hermes's `format_process_notification` (see the test) and run the tests: a changed format would otherwise show raw text again.
- **The connection dot's freshness rules live in `lib/health-store.ts` (`summarizeHealth`)**: an open request counts as connected only while it is younger than the resource's window, the 15-second grace after returning to the app counts from that moment, and one failure is a blip. A resource that polls by long-poll must call `pending()` before each request (as the chat does), or its window has to cover the whole hold plus slow networks. `lib/poll.ts` aborts a request left open across a background stint; a `run` must treat an aborted signal as "not a failure". A polled resource's window must come from the interval it really uses, `staleWindow(interval)`, including its hidden-tab or live-channel schedule: a hand-set constant shorter than the interval is a yellow dot with nothing wrong ("Today stale 48s").
- **Hermes's own chat texts are recognised by their wording** (`chat_state.py`: `approval_announcement` reads `EA_HEADER_TEXT` from `gateway.platforms.base_exec_approval` through `hermes_api`, with a copy as fallback; `unwrap_cron_failure` matches the "⚠️ Cron '<name>' failed: <error>. …" line from `cron/scheduler_failure_copy.py` and the "failed N runs in a row" sentence from `cron/scheduler.py`). A rewording upstream shows the approval twice (the chat-controls contract fails at "its announcement is not shown as a notice") or turns a failure card back into Hermes's text (`test_chat_state.py` CronFailureTests cover the three shapes, bare and inside the "Cronjob Response" envelope). The card's Run again and Pause assume the job belongs to the `chief` profile, whose gateway posts the notice.
- **The long-poll's "I track this" keys must survive a blank value.** `/transcript?wait=` breaks on a change only for keys the caller sent (`clarify`, `notice`, `bg`, `draft`); a caller with none yet sends the key blank. `server.py` parses the query with `keep_blank_values=True`; with Python's default the blank was dropped, read as "not tracked", and a conversation's first question, notice or draft frame never woke a waiting poll (found while adding drafts; `test_bridge.py` "blank query values reach the long-poll"). A new helper that reads `req.q(name)` must treat "" as a value, not as absence.
- **Replies stream as Hermes draft frames** (`adapter.supports_draft_streaming` / `send_draft`, kept in `chat_state.record_draft`; `streaming.enabled` set by provisioning, Hermes's stream consumer in `gateway/stream_consumer_transport.py`). `send_draft` must never fail: a refused frame makes Hermes fall back to real partial sends (`send` + `edit_message`), which would land in the outbox as notices. The draft stays until the turn ends (`live_transcript` clears it once `generating` is false; clearing at the final send flashed "thinking" before the stored row landed), and the chat drops a draft once a reply has landed for it (`settledDraft` in `chief-chat.tsx`), never by comparing text: a repeated reply would match an older one. The cursor glyph is stripped by name (`▉`, Hermes's default `streaming.cursor`). The chat-controls contract fails at "the reply streams as a draft" if Hermes stops probing the adapter.
- **Retry after a failed start runs the whole sequence again against children that may still be running.** `choosePorts` must treat a port this run's own supervisor holds as ours (`decidePorts` in `ports.ts`), `claimGateway` must not end the gateway this run's supervisor is starting or running (`isOrphan` in `gateway.ts`: the pid file names Hermes's Python process, the supervisor's child is the launcher, so the rule goes by the supervisor's state, not the pid), and a supervisor that recovers on its own re-runs the boot (`recoversBoot` in `boot.ts`). A new step that starts something must survive being run twice. Test map: `tests/boot-seams.test.ts`, `tests/boot.test.ts` "a start that recovers".
- **Nothing in the main process may block.** `killTree`, `requestScopedStop` (`gateway.ts`) and `zipFolder` (`diagnostics.ts`) are asynchronous; a `spawnSync` of a slow helper froze the window for its whole wait. The one left is `installPackage`, which hands the package to Windows and quits.
- **The design-rules test reads every component** (`tests/design-rules.test.ts`): a text field must use `field()`/`Input`/`Textarea`/`Select` unless its file is on the bare-field list (a field drawn inside a framed search box or the composer), a button must carry `press`, `btn(` or a role (or be a text link, by `underline`), and no `rounded-[…]`. A new one-off style fails the test; the answer is a primitive or a token, or a reviewed entry on the allow-list. The parser tracks braces so an arrow function inside a prop doesn't end the tag early (the first measurement didn't, and counted 105 offenders where there were 18).
- **Each surface sits in a `SurfaceErrorBoundary`** (`components/ui/error-boundary.tsx`, mounted in `command-shell.tsx`). A new surface must be wrapped too, or its crash goes to the app's error page and takes the chat with it. The boundary catches render errors only; an error inside an event handler or a promise still needs its own `try`.


## Upstream Hermes: next forms, drift and retries

`hermes/pin.json`, `hermes/patches/`, `packaging/payload/prepare_source.py` (`apply_queue`), `packaging/upstream/{candidate,drift,update_pin,upgrade_notes}.py`, `.github/workflows/upstream.yml`, `.github/workflows/upstream-drift.yml`. Test map: `hermes/tests/test_upstream_tooling.py`, `test_hermes_api.py`.

- **A patch upstream's newer code no longer fits gets a `next` form, not an edit.** The current file keeps building the current pin; the new form goes beside it as `<name>.next.patch` (or a list of forms when upstream's release candidate and main differ, like 0004's `.next` and `.rc`), listed under `"next"` in the entry. `prepare_source.py` tries the entry's own file first, then each form. When the pin moves, `update_pin.py --applied` writes the form that applied over the entry's file and deletes every form; the provenance check only ever hashes the entry's own file. `test_upstream_tooling.py` fails on a listed form that's missing or a patch file nobody lists.
- **The nightly drift check reads Hermes, it doesn't import it.** `drift.py` parses each module the bridge uses with `ast`, so a name made at import time is invisible to it: a module that defines `__getattr__`, star-imports or passes `globals()` to a call (Hermes's `*_registry` modules do `_registry.export(globals())`) is taken on trust. The real import check is the compatibility suite's "Hermes names the bridge uses".
- **A Hermes rename is spanned with `"new|old"`** in `hermes_api.CAPABILITIES` and `hermes_api.get(module, "new|old")`: one bridge works on both sides of the rename, and the old half can go once the pin is past it. Hermes 2026.10 renamed `_STT_MODEL_CONFIG_KEY` to `STT_MODEL_CONFIG_KEY` this way.
- **A blocked upgrade retries itself when our side changes.** Every candidate PR and blocked issue carries `<!-- attempt:<key> -->`, a digest of the patches, the bridge plugin, the contracts, the suite and the payload builder (`candidate.attempt_key`); the daily poll skips a tag only when something with today's key exists (or a PR for it is open or merged). Closing the issue by hand doesn't retry it; changing one of those inputs does. Older blocked issues for the tag are closed when a new attempt reports.
- **A forced run never downgrades.** The pin can sit on upstream main past its base tag, so a stable tag that isn't a descendant of the pinned commit would drop commits the app ships. `candidate.py` reports `contains_pin`, and a forced run only builds a tag that is newer or contains the pin.
